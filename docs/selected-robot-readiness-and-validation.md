# 指定机器人调度：稳定性改进与验收计划

## 结论与边界

目标版本限定为单实例、单楼层、业务已指定机器人；地图、作业点、停靠位和路线足够充裕。
本次不扩展自动选车使用权，不引入 CBS、自动让路或多实例共享内核。

当前可开展受控功能联调，但不能仅凭代码回归认定达到商用标准。使用权、外部作业和交通占用的持久化与重启对账已补齐，
详见 runtime-recovery.md；仍未完成真实 RMS、数据库、质检服务和报告服务参与的 30 台持续验收。

调度负责移动、任务状态、交通占用和使用权。质检动作、检测结果、报告生成及 MES 提交由业务服务负责。
本项目测试报告记录的是调度验收结果，不是产品质检报告。

## 本轮请求幂等规则

新业务建议使用通用移动请求，以字符串 task_id 避免旧 goto-place 整数 ID 的取值限制：

```http
POST /api/v1/scheduler/dispatch_task
Content-Type: application/json
```

```json
{
  "taskflow_id": "1001",
  "task_id": "run-001-R001-move-work-01",
  "robot_code": "R001",
  "task_template_type": "go_to_place",
  "nav_end_point": "W1",
  "parameters": {"idempotent": true}
}
```

- parameters.idempotent 必须是 JSON 布尔值 true；不传时保留旧行为。
- 启用后，该 task_id 应作为全局唯一业务请求键。相同载荷重试返回原 scheduler_request_id，不再次下发。
- 相同 ID 改机器人、任务流、目标点或参数返回 409；失败后决定重做时，也必须使用新 ID。
- 终态请求重发返回原任务状态；应按 scheduler_request_id 查询后续执行结果。
- 保障范围是单实例准入和仍保留的请求记录。历史记录清理之后不承诺永久去重，更不提供多实例唯一性。
- 网络超时先重试原请求或查询原请求，不能立刻换新 ID，否则会被视为另一项新任务。

## 代码回归覆盖

ThirtyRobotWorkflowTest 使用真实调度内核、拓扑图、交通登记、命令执行器和使用权登记，RMS 为隔离模拟：

1. 30 台车、30 个作业点、30 个停靠位、30 条独立双向路线。
2. 首批 30 条导航在模拟网关内汇合后才完成，避免用串行执行冒充并发。
3. 每台连续执行十轮：取得使用权 → 移动到作业点 → 开始外部作业 → 确认结束 → 移动到停靠位 → 释放。
4. 合计 300 个业务交接闭环、600 次移动；检查终态、登记回收、物理驻留保留，并确认调度未发质检动作。
5. 另用 30 个并发申请争用同一段和同一作业点，十轮验证只能有一个申请成功，驻留接续后仍阻塞其他申请。

其他回归覆盖相同请求 30 次并发重试、改变请求冲突、终态重放、受理失败收口、
完成帧早于 HTTP 返回、ack 异常、中间状态不误报失败、目标附近仍导航，以及慢清单任务隔离。

模拟不包含真实 HTTP 延迟、数据库写入、轮询帧滞后、车体尺寸、机器人实际走行或业务报告生成。
这些用例通过只能说明指定场景下的代码闭环正确，不能直接推导“30 台实车已稳定运行”。

## 业务联调顺序

每个机器人使用独立任务流，沿用同一 taskflow_id。旧 assign-task 的 ID 是整数，新通知与 dispatch_task 使用对应字符串。

| 步骤 | 调用或检查 | 通过条件 |
| --- | --- | --- |
| 1. 取得使用权 | POST /api/v1/scheduler/assign-task | 返回成功，GET /api/v1/scheduler/robot-use 显示正确持有者 |
| 2. 移动 | POST /api/v1/scheduler/dispatch_task，类型 go_to_place，开启幂等 | 保存 scheduler_request_id；同载荷重复提交不能重复移动 |
| 3. 确认到点 | GET /api/v1/scheduler/tasks/status?scheduler_request_id=... | task_status=completed，且没有取消标记，RMS 位置与实际到位符合业务精度 |
| 4. 开始作业 | POST /api/v1/scheduler/external-operations/start | 返回成功后才能下发 RMS 动作；409 时先确认尚未退出的调度任务 |
| 5. 质检 | 业务服务调用 RMS | 使用独立业务作业 ID；等待实际终态，采集检测结果，不以“请求接受”代替执行完成 |
| 6. 结束占用 | POST /api/v1/scheduler/external-operations/finish | 确认动作结束、设备允许移动后通知；开始和结束 operation_id 相同 |
| 7. 报告 | 业务服务生成并查询报告 | 报告关联 taskflow_id、业务作业 ID、机器人、作业点和结果；重复回调不能产生重复报告 |
| 8. 让出工位 | 再提交一项 go_to_place 到停靠位 | 使用新 task_id，等待未取消的 completed；工位驻留消失、停靠位驻留出现 |
| 9. 释放使用权 | POST /api/v1/scheduler/release-robot | 使用权清空、外部作业为空；停靠位物理驻留仍存在 |

报告可以在设备动作安全结束后与离场并行处理，不应因生成报告耗时而让机器人一直占住工位。
报告生成失败由业务重试报告步骤，不能因此重做移动或再次质检。
若质检失败或超时，先确认本体已停止/恢复再结束外部占用；不能把 finish 当作强制取消。

重要兼容语义：活动任务取消可能表现为 completed + cancellation。
业务应检查 data.raw.task_state.cancellation（或业务侧已登记的取消状态），不能只看 completed 就开始质检。

## 分阶段验收

以下为建议门槛，不是已测性能承诺。先验证单台，再扩大规模；每轮保留运行 ID 与原始证据。

| 阶段 | 场景 | 验收要点 |
| --- | --- | --- |
| A | 单台十轮真实闭环 | 移动、质检、报告、离场、释放全部关联；无误到点、误作业、重复报告 |
| B | 5 台共享作业点 | 有序排队，离场后继续执行；报告故障不能占住工位 |
| C | 30 台各自工位和停靠位，十轮 | 300 个业务闭环、600 次移动、300 份业务报告；无任务丢失、重复执行、错误释放或长期残留 |
| D | 30 台充裕路网中共享若干交叉口/工位 | 实测实际车体无冲突；等待原因有机器人与资源，阻塞解除后恢复；不以故意堵路作为本轮目标 |
| E | 正常异常 | 网络短时超时、重复请求/通知、一台离线、作业失败、取消；其余车辆继续处理，异常车占用不被提前释放 |
| F | 持续运行至少 8 小时 | 内存和队列无持续增长、连接池不耗尽、状态轮询不长期滞后，已结束任务最终收口 |
| G | 恢复与部署 | 验证已补充的导航中、外部作业中重启恢复；停止确认前不得实际执行新导航 |

建议记录：受理耗时 P50/P95/P99、实际状态帧间隔、任务/交通等待耗时、失败原因、
RMS 命令数量、任务与 operation_id 重复数量、DB 写入耗时、内存、线程和连接池占用。
无故障独立路线场景要求所有任务完成；共享场景不能有无法解释的等待或静默失败。
受理 P95 小于 1 秒、正常状态帧间隔小于 5 秒可作为首轮参考，需根据部署机器及 RMS 实测共同确定。

## 下一项优先级

使用权/外部作业持久化及重启对账代码已补充；下一项为有界准入与停机收口。
不建议以集成 CBS 代替这些生命周期能力，也不需要为了凑模块把质检和报告搬回调度。
首次升级和实车恢复验收完成前，仅限单实例受控联调：部署前暂停业务、确认无在途导航与外部作业，构建完成后再启动。
