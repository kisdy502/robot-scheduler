# 网上开源 RMF 存在的问题（踩坑记录 → 本项目对策）

> 来源：开源 RMF（rmf_core + fleet adapter + rmf-rest-api）生产/联调实践踩坑。
> 每条按 **现象 → 根因 → 影响 → 本项目（robot-scheduler）对策** 组织；对策均已实现或有明确设计，避免重蹈覆辙。

## 1. 通讯模型：ROS2 topic 请求响应交互不方便

**现象**
- 基于 ros2 topic 的命令交互，没有天然的请求-响应语义，回执靠自定义 topic 拼接。
- 跨机部署时 ros2 domain id 配置敏感，冲突时节点互相不可见，且**没有任何报错提示**。

**根因**：topic 是广播模型，RMF 在其上自建了 api_response/task_state_update 等异步回执，链路环节多（api server → schedule → negotiation → fleet adapter → 机器人），任何一环断开上层都感知不到具体位置。

**影响**：联调排障成本高，"发了没回"是常态；上层任务流无法做同步语义的失败处理。

**本项目对策**
- 南向统一走 **HTTP REST（RMS 网关）**：navigate/stop/start-activity 等 8 端点，请求即达，错误即回。
- 回执闭环：命令带 `rmf_command_uid`（sched:robot:seq），状态帧 `completed_commands` 三级匹配（uid 精确 → cmd_id → last_completed_request 兜底），超时/取消有 generation 防串。
- 命令重试：SUCCESS/RETRY/IMPOSSIBLE 三态映射，RETRY 退避重试 3 次。

## 2. 错误提示万金油，失败原因不明确（最坑）

**现象**
- `Failed to start task: tf-241087756613591040-241087756689088512` —— 任务失败了只给任务号，没有根因，等于没提示。
- 经典万金油：`RMF api_response timeout; request was published but RMF did not acknowledge it` —— 没有机器人、机器人离线、节点没启动、ros2 domain id 冲突、机器人不在地图点位、机器人区域问题……全都报这一条，自己慢慢查。

**根因**：分布式链路上任何环节的失败都被收敛成"超时"一种表达；RMF 内部缺少错误分类体系，回执不携带错误码/错误源；异步协商（negotiation）失败的语义没有回传通道。

**影响**：现场排障全靠猜和二分法重启；上层无法按失败类型做差异化处理（重试/换车/告警/放弃）。

**本项目对策（失败原因精准化，已落地的分类）**

| 场景           | 提示（三要素：位置+原因+下一步）                                                                                                |
|--------------|------------------------------------------------------------------------------------------------------------------|
| 目标点不存在/地图不匹配 | `目标点位不存在: Goal_uX0Ef`（点名到具体点位 id；充电目标不可解析时自动选桩并记日志）                                                              |
| 车队组没机器人      | 受理即 409：`no robot is registered in fleet group [xxx]; please check RMS robot group assignment (group_no)`，不傻等 60s |
| 机器人不可派发      | `机器人 xxx 不可派发（离线/离图/外部任务执行中/decommissioned），等待超时 30s`                                                            |
| 交通资源冲突       | 区分两类：`目标点 P52 被静止机器人 xxx 驻留占用` / `必经路径被其他机器人长期占用`，并给出等待上限                                                        |
| 自动分配超时       | `自动分配超时：无可用机器人在 60s 内`                                                                                           |
| 本体忙拒绝        | 原文透传 `已有在途任务 xxx，请先 stop/pause [BODY_START_TASK_REJECTED]` + 中文化解释；并自动 stop 清除后重试一次                              |
| 导航分段失败       | `导航分段未完成 [P52->P33]: <机器人回执原文>`（点到具体段）                                                                           |
| 命令等待超时       | `命令等待超时 120s（阶段: 导航段 P52->P33）`      

配套机制：机器人回执 `raw_result.data.msg` 原文保留可追溯 + 常见拒绝原因中文化；分配评分明细（ETA/电量惩罚/总分）随任务状态透出，"为什么选这台车"可解释。

**团队规约**：新增任何失败路径，提示必须含"位置 + 原因 + 建议动作"三要素，禁止只报任务号或统一超时。

## 3. 场景/地图切换要重启程序；坐标系转换复杂
场景切换，无法热切换，要重启程序
配置复杂，RMF地图坐标体系单独搞一套，每次都要把slam地图坐标系转rmf坐标系，需要写一大堆非结构化的转换逻辑

充电管理，不够强大和灵活，上层应用层往往有定制充电配置，rmf无法满足，鸡肋
