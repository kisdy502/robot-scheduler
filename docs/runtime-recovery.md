# 使用权、交通占用持久化与重启对账

## 本轮范围

正式装配使用 t_robot_runtime 作为运行正本，保存每台机器人的：

- 任务流使用权、当前外部作业、最近一次已结束外部作业及时间。
- 已预约的点和路段、实际驻留点/段、停止确认状态、绑定的地图名称和版本。
- 实际进入执行的内核任务 ID，以及最近分配的命令序号；重启后接续，避免旧回执误结束新命令。

纯内存实现保留给独立构造和单元测试，不注册为正式仓储 Bean。正式服务缺少持久化实现或数据库不可用时不能用空白内存降级启动。
对外接口路径、请求字段、成功信封、取消语义和外部作业开始/结束调用顺序不变。

## 写入与失败边界

1. 取得使用权、释放使用权、开始或结束外部作业，先提交数据库事务，再修改内存并回复成功。
2. 交通申请、渐进释放、驻留接续在单实例锁内保存正本；写失败不返回新预约成功。提交结果可能不确定时，保守冻结新旧候选资源的并集，停止确认并成功落库后才收缩。
3. 释放旧预约失败时继续冻结旧资源，后续由停止确认处理。不会因为数据库失败或超时自动清空占用。
4. 静止机器人相同点位的重复位置帧不重复写盘；审计只在运行正本写成功后发出，审计故障不撤回已提交正本。
5. 命令序号在下发之前提交，允许跳号，不允许倒退复用。首次初始化使用正整数时间种子避开旧版本常见的小序号。
6. 运行正本使用独立事务，并在提交完成后才退出单实例锁；调用者的其他事务回滚不能撤回已经确认的占用。

使用权相关写入失败返回 HTTP 503 + detail。上层保留原 taskflow_id、operation_id 重试或查询，不应换 ID 绕过。
数据库断开期间无法承诺新的动作已经送达；原有占用保持保守阻断，恢复后继续对账。

## 重启行为

| 重启前状态 | 恢复处理 |
| --- | --- |
| 已取得使用权，尚未提交移动 | 恢复同一持有者，不自动产生移动任务 |
| 进行中的外部作业 | 恢复原 operation_id 和开始时间，保持忙碌，不自动 finish，也不因重启单独发 stop |
| 外部作业已结束 | 保留最近一次完成通知的幂等结果，原使用权仍保持，除非此前已经释放 |
| 已释放使用权 | 不恢复为已占用；物理驻留独立保留 |
| 尚未完成的导航预约 | 恢复全部尚未释放的点段，转为等待停止确认，不自动重放导航 |
| 已到点、没有未来路线，但内核动作尚在执行 | 根据执行任务 ID 恢复停止对账，覆盖旧质检/充电等内核动作；排队任务不设置该标记 |
| 已有停止保留 | 保留占用，丢弃旧进程的“停止已接受”标记，重新确认 |
| 只有点位/路段驻留，无未来预约 | 恢复物理障碍，不因没有任务而释放，不凭空增加导航停止请求 |
| 机器人仍离线 | 不会因时间流逝或重启清空点位和路段 |

导航恢复沿用原 FleetManager 机制：收到新位置帧后下发 stop；RMS 接受后再采集三帧稳定位置和朝向，
最后在同一事务中把旧预约收缩为实际驻留。确认期间，相关机器人不能接受实际执行的新导航，其他机器人仍避开其旧资源。
若外部作业在重启前就因失联进入停止保留，则继续处理该停止保留；这与“纯外部作业不因重启自动停止”是两个状态。

任务状态仍沿用原启动规则：未终态的调度任务标记为 failed，不自动重跑。
将任务标记失败不等于释放交通预约。上层先查询任务、使用权和外部作业状态，再决定接续业务或使用新 task_id 重做移动。
中断也不等于动作从未执行：重做质检或生成报告前，上层应先核对原 RMS 任务和业务结果，避免盲目重做。
执行标记按任务 ID 比较后清除，旧线程退出不能清掉新任务的标记；结束写盘失败会阻止业务接续并后台重试收口。

## 地图恢复

恢复的占用必须对应原地图名称及 version。启动允许加载这个版本的原图，即使已有恢复占用；这不是切图或清空资源。
找不到原图或激活版本不符时停止启动，不回退为无图服务，不套用另一张图的点位 ID。
原图加载后，常规切图仍受任务绑定、物理驻留、停止保留及外部作业门禁约束。

## 首次升级与兼容性

新增 Flyway V6 创建 t_robot_runtime，V7 增加 scheduler_task_id 执行标记及内核/外部作业互斥约束，不修改旧业务表或历史迁移。
JSON 时间仍为 Unix 毫秒，数据库时间为 TIMESTAMPTZ；内部不增加 SLAM 坐标变换。
运行数据不自动过期，机器人离线不会触发删行或资源清理。命令序号也不能因清理历史任务而重置。

首次从旧版本升级时，旧进程的内存数据不可能由一张新空表还原：

1. 暂停上层派发，等待业务和外部作业结束；确认所有在途机器人已经停止。
2. 完整停止旧进程，保留匹配的激活地图存档，备份数据库。
3. 构建完成后启动新版本，由 Flyway 自动执行 V6、V7，按首次位置帧建立驻留正本。
4. 恢复上层任务流使用权登记后，再恢复业务派发。

以后运行产生的状态可由新版本自动恢复。服务仍是单活，不能两个实例同时调度同一车队；滚动发布应避免旧新实例重叠运行。
本轮没有实现多实例调度、完整优雅停机或离线机器人人工移走后的受控强制解除流程。不能直接删运行表作为解除占用手段。

## 验证

- 核心测试：使用权/作业跨对象重建、写入失败不放行、旧 stop 标记失效、原图恢复与版本拒绝、物理驻留保留。
- 30 台恢复回归：十五台在途导航重新停止确认，十五台外部作业保持忙碌，导航不重放，外部作业不被误停。
- 命令测试：重建执行器后序号继续增长，旧序号回执不匹配新命令。
- 装配测试：正式内核选择持久化交通实现，使用权与命令执行器使用所注入的同一仓储。
- 独立 PostgreSQL 测试：真实 V6/V7、JSONB、NULL 清空、事务提交、外层事务回滚不撤回正本、唯一使用权约束、并发序号及执行标记按 ID 收口。

数据库测试仅对显式指定的本机一次性 scheduler_recovery_test 库启用，默认不连接外部基础设施。
这些测试不是 30 台实车断电或生产数据库故障演练；正式部署后仍需验证真实 RMS 停止回执、位置帧和业务接续。
